TASK: Rebuild A-Level (UACE) grading from the paper level up. The current
build grades each subject as one blended percentage (BOT/MOT/EOT weighted
average) run through a percentage→letter table. That is not how UACE
grading works and must be replaced, not patched.

=====================================================================
0. WHY THIS IS WRONG (read before touching code)
=====================================================================
Every UACE subject is composed of 2, 3, or 4 independently-marked
PAPERS. Each paper is scored 0-100% and banded to a 9-point scale
(D1-F9). The subject's Principal letter grade (A-E, O, F) is NOT an
average of paper percentages — it comes from matching the specific
COMBINATION of paper bands against a published rule table, where the
worst paper constrains the outcome (in 3/4-paper subjects) and F9
handling has its own non-obvious downgrade logic. A single blended
percentage cannot feed this — there is no "worst paper" to find, and
no per-paper F9 to detect. This is the root fix.

=====================================================================
1. DATA MODEL CHANGES
=====================================================================

1a. subjects table — add:
    - paper_count (tinyint, 2/3/4)
    - subject_category (enum: 'science' | 'non_science') — needed for
      one specific rule exception (see 3d)
    - is_subsidiary (bool) — General Paper / Sub-Math / Sub-ICT etc.

1b. NEW TABLE subject_papers (definition, not results):
    - subject_id
    - paper_number (1..paper_count)
    - paper_code (e.g. "P210/1") — what prints on the report card
    - display_name (e.g. "Paper 1: Political Organisation")

1c. NEW TABLE paper_results (replaces "one percentage per subject"):
    - enrollment_id, subject_id, paper_number, term/exam_cycle_id
    - raw_percentage (nullable — see 1d)
    - status: enum('scored','absent','withheld') — NEVER store a raw
      0 or null to mean absent; status is an explicit separate field
    - paper_grade (computed: D1-F9, or null if status != 'scored')

1d. Grade-entry UI/API must force a choice per paper: enter a score,
    OR mark Absent, OR mark Withheld. No paper may be left blank and
    saved — this is a hard validation, not a UI nicety, because
    downstream aggregation cannot tell "0%" apart from "not sat"
    otherwise.

=====================================================================
2. CONFIGURABLE LOOKUP TABLES (admin UI, zero code changes to edit)
=====================================================================
Everything UNEB-specific becomes DATA, editable from an admin screen,
versioned by exam_cycle_id so a ruleset change never mutates history.
Every table below needs: create, edit, clone-into-new-version,
activate/deactivate. Never overwrite an active version in place —
always clone-then-edit, so historical reports stay reproducible.

2a. TABLE: paper_band_boundaries (per exam_cycle_id)
    columns: band_code (D1/D2/C3/C4/C5/C6/P7/P8/F9), min_pct, max_pct
    Used to convert paper_results.raw_percentage → paper_grade.
    Seed with the current confirmed boundaries:
      D1 85-100, D2 80-84, C3 75-79, C4 70-74, C5 65-69,
      C6 60-64, P7 50-59, P8 40-49, F9 0-39
    Admin can edit these directly if UNEB revises bands — no deploy.

2b. TABLE: combination_rules (per exam_cycle_id, per paper_count)
    columns: paper_count, rule_order (int — first match wins),
             pattern (ordered array of band_codes, e.g. ["D1","D1","C4"]
             — store as a matcher, not literal permutations: define
             each rule as "worst band in set" + "count of bands below
             threshold X", NOT as an exhaustive list of every possible
             tuple. See 3b for exact matcher shape.
             subject_category_override (nullable — for the science
             exception, see 3d)
    resulting_grade (A/B/C/D/E/O/F)

    THIS TABLE MUST BE SEEDED FROM THE ACTUAL UNEB COMBINATION-MATRIX
    ANNEXURE, NOT FROM ILLUSTRATIVE "E.G." EXAMPLES. If the real
    annexure isn't in hand yet, seed only the patterns that are 100%
    confirmed, and see 3c for what happens on an unmatched input —
    do NOT guess-fill gaps with inferred patterns.

2c. TABLE: grade_points (per exam_cycle_id)
    columns: grade_code (A/B/C/D/E/O/F), points (int)
    Seed: A=6, B=5, C=4, D=3, E=2, O=1, F=0
    This exists as its own versioned table (not a hardcoded switch)
    specifically because NCDC has signalled the letter set itself may
    collapse to A-E only in a future cycle — when/if that happens, a
    new exam_cycle_id gets its own grade_points + combination_rules
    rows, old students' reports keep computing against the version
    that was active when they sat, nothing in code changes.

2d. TABLE: subsidiary_config (per exam_cycle_id)
    - pass_threshold_pct (default 40 — matches F9/P8 boundary, i.e.
      P8 and above = Pass)
    - pass_points (default 1), fail_points (default 0)

2e. TABLE: max_aggregate_config (per exam_cycle_id)
    - Don't hardcode "20." Compute it as:
      (best 3 principal subjects × max points in grade_points table)
      + (count of required subsidiaries in the combination × 
      subsidiary_config.pass_points)
    - This makes the ceiling correct automatically if a combination
      has a different subsidiary count, or if grade_points values
      ever change.

=====================================================================
3. THE GRADING ENGINE (uaceBreakdown, rebuilt)
=====================================================================

3a. Per subject, per student, per exam_cycle:
    1. Pull all paper_results for that subject where status='scored'.
    2. If ANY paper for that subject has status='absent' or
       'withheld' AND it's a required paper → subject result =
       "INCOMPLETE", do not compute a letter grade, surface on
       exception report (see 4). Never silently drop the paper from
       the combination calc.
    3. Convert each scored paper's raw_percentage to paper_grade via
       paper_band_boundaries (2a).
    4. Sort the resulting band_codes worst-to-best.
    5. Walk combination_rules (2b) for this paper_count, in
       rule_order, testing each pattern-matcher against the sorted
       set. First match wins — do not average, do not pick "closest."
    6. If NO rule matches → do not default to Fail or Pass. Output
       status "UNMATCHED — MANUAL REVIEW REQUIRED" and add to the
       exception report. This is the safety valve for exactly the
       tie/edge cases (e.g. two P7s + one C6) that aren't cleanly
       covered by the illustrative examples — a wrong guess here is
       worse than a flagged gap.
    7. Resulting grade → points via grade_points (2c).

3b. Pattern-matcher shape for combination_rules — implement as a
    small rule DSL, not literal tuples, e.g.:
      { "worst_at_best": "C3", "others_at_best": "D1", "count_others": 2 }
    meaning: worst paper is C3-or-better, and the other 2 papers are
    D1-or-better. This is what lets admins add/edit rules from a UI
    without needing every literal permutation enumerated — but the
    matcher logic itself (comparing band ranks) is code; only the
    threshold values per rule are data.

3c. Unmatched-pattern handling (from 3a.6): build a small admin queue
    view — "N subject results pending manual grade confirmation" —
    where a registrar sees the raw paper grades and assigns the
    correct letter by hand, which also creates a new combination_rules
    row (with admin confirmation) so the same pattern auto-resolves
    next time. This is how the rule table gets completed correctly
    over time instead of being guessed upfront.

3d. Science-subject exception: combination_rules rows may set
    subject_category_override to force a different resulting_grade
    when subject.subject_category = 'science' matches a specific
    pattern (the documented case: two F9 + one P7 = Fail for science
    subjects specifically, not the general O-grade outcome). Engine
    checks category-specific rules before falling through to general
    rules of the same paper_count.

3e. Subsidiary subjects: single-paper subjects skip the combination
    matrix entirely — just raw_percentage vs subsidiary_config
    threshold → pass/fail → points. Keep this as a distinctly simpler
    code path; do not force it through the paper-combination engine.

3f. Total = sum(principal points, best 3) + sum(subsidiary points),
    displayed as "X / max_aggregate_config value" — never a hardcoded
    "/20" string anywhere in a template.

=====================================================================
4. REPORT CARD & RANKING
=====================================================================
- Report layout must print one row per PAPER (paper_code, %, band),
  grouped under the subject, with the Principal/Subsidiary grade and
  points shown once per subject — matching the per-paper card
  structure already agreed, not a blended single line.
- A subject with status INCOMPLETE or UNMATCHED prints that explicit
  state on the card (not a blank, not a guessed grade) — official-
  facing views only ever show a fully-resolved state: a grade, ABS,
  INCOMPLETE, or the total is marked provisional until resolved.
- Class ranking must exclude any student with an unresolved
  INCOMPLETE/UNMATCHED subject from the "final" ranking pass, or
  clearly mark their rank as provisional — do not rank against a
  guessed number.
- AoI/formative marks (already agreed) continue to print as a
  separate, unblended section per subject — they do not feed
  combination_rules or points in any way, at any level.

E. SUBSIDIARY SUBJECTS (single paper) — CONFIRMED

---------------------------------------------------------------------
G. AGGREGATE CEILING (2e) — CONFIRMED FOR CURRENT (LEGACY) MODEL
---------------------------------------------------------------------
Best 3 principal subjects x 6 points max = 18
+ General Paper subsidiary pass = 1
+ Sub-Math OR Sub-ICT subsidiary pass (student takes exactly one) = 1
= 20 points maximum, NOT 17.

There is a SEPARATE, university-specific weighting layer (used by
e.g. Makerere/JAB for programme admission) that multiplies principal
grade-points by course-specific factors (best "essential" subject x3,
second x2, third x1) plus flat 1-point subsidiaries. This produces a
different, programme-dependent number and must live in its own
AdmissionsWeightingProfile table, never merged with the 20-point
UNEB aggregate above. If the school ever wants to show a projected
university-weighted score, that is an entirely separate configurable
profile per programme, not a variant of the core grading engine.
